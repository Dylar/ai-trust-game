# Development Commands

The repository root `Makefile` is a small entrypoint that includes focused files under
[`../infrastructure/make`](../infrastructure/make/):

- `common.mk` for shared defaults
- `quality.mk` for Go and Flutter quality checks
- `compose.mk` for the optional local compose stack
- `k8s.mk` for Kubernetes deployment commands

## Compose Stack

The compose stack is optional local development tooling. It is not part of the Kubernetes deployment path.

Compose uses `COMPOSE_FILE`, which defaults to `infrastructure/docker/compose/compose.yml`.<br>
Container-to-container and browser-to-backend communication is local in that file.<br>
The root compose file includes the backend and web compose files from the same directory.<br>
Model provider values are read from `COMPOSE_ENV_FILE`, which defaults to
`infrastructure/docker/compose/env/<COMPOSE_MODEL_ENV>.env`.<br>
Before each compose command, Make checks that the compose file and selected model env file exist and that required
model variables such as `LLM_PROVIDER` are present.

### Commands

Builds and starts the local stack using the default `static` model env file.

```bash
make compose-up
```

Builds and starts the local stack with another prepared model env file, for example after copying
`groq.env.example` to `groq.env` and filling its values.

```bash
make compose-up COMPOSE_MODEL_ENV=groq
```

Restarts the current compose containers without rebuilding the images.

```bash
make compose-restart
```

Stops and removes the local stack started through the Docker Compose file.

```bash
make compose-down
```

Follows the combined logs of the current compose stack.

```bash
make compose-logs
```

## Kubernetes

The Kubernetes commands are for the Raspberry Pi cluster deployment path, not for local development.
For local work, use the compose stack above.

The usual question is: "Do I want the current local code on the cluster?"
If yes, use `manual-deploy`. It builds the prepared service images, pushes them to GHCR with a generated
`manual-deploy-<sha>-<date>-<time>` tag, and then rolls the selected environment out with Helm.
The other commands are mostly checks, diagnostics, or single-step escape hatches.

`ENV` selects the target environment, for example `dev`, `test`, or `prod`.
`SERVICE` is optional. If omitted, deploy commands target all prepared services. If set, only that service is handled.

### Normal Flow

Builds, pushes, and deploys the prepared services for the selected environment.
The image tag is always generated by Make as `manual-deploy-<sha>-<date>-<time>`.

```bash
make manual-deploy ENV=dev
```

Builds, pushes, and deploys only one service.

```bash
make manual-deploy SERVICE=main-service ENV=dev
```

Deploys already published images for all prepared services using the current Git commit SHA as the image tag.

```bash
make k8s-deploy ENV=dev
```

Deploys an already published image for one service using the current Git commit SHA as the image tag.

```bash
make k8s-deploy SERVICE=main-service ENV=dev
```

### Checks And Diagnostics

Shows the deployed Kubernetes workloads and services labeled as part of `ai-trust-game` across all namespaces.
Use this after a deploy to check whether pods, deployments, and services are visible.

```bash
make k8s-status
```

Lints the Helm chart and renders each selected environment without applying it.
Use this before deploying when you changed charts or values.

```bash
make k8s-lint
```

Runs the same Kubernetes validation for another prepared service.

```bash
make k8s-lint SERVICE=frontend-web K8S_ENVS='dev test prod'
```

Renders the Kubernetes manifests for the selected service and environment through Helm.
This prints what Helm would send to the cluster, without applying it.

```bash
make k8s-template SERVICE=main-service ENV=dev
```

Shows the Kubernetes context and nodes from the project kubeconfig.

```bash
make k8s-context
```

Prints the automatic manual deploy tag format without triggering a workflow.

```bash
make manual-deploy-tag
```

### Individual Steps

Builds the selected service image from the local working tree and pushes it to the image repository from the selected
Kubernetes values file.
Use this only when you intentionally want to separate image publishing from deployment.

```bash
make k8s-build-push SERVICE=main-service ENV=dev IMAGE_TAG=dev-local
```

Installs or upgrades the selected service and environment through Helm. If `IMAGE_TAG` is omitted, the current Git
commit SHA is used as the image tag.
Use this when the image already exists and you only want to update one Helm release.

```bash
make k8s-apply SERVICE=main-service ENV=dev IMAGE_TAG=dev-local
```

Installs or upgrades the Flutter web frontend using values from `app/k8s`.

```bash
make k8s-apply SERVICE=frontend-web ENV=dev IMAGE_TAG=dev-local
```

Installs or upgrades only the app entry Helm release for the selected environment.
The app entry is the shared cluster entrypoint for the deployed environment.

```bash
make k8s-apply-entry ENV=dev
```

### Cleanup

Uninstalls the selected Helm release from the selected environment namespace.

```bash
make k8s-delete SERVICE=main-service ENV=dev
```

Uninstalls the app entry Helm release for the selected environment.

```bash
make k8s-delete-entry ENV=dev
```

Manual image publishing is also available through the `Publish Images` GitHub Actions workflow.

## Quality Checks

### Commands

#### Tests

Runs Go and Flutter tests.

```bash
make test
```

Runs the full Go test suite.

```bash
make test-go
```

Runs the Flutter test suite from `app/`.

```bash
make test-flutter
```

#### Linters

Runs Go linting and Flutter static analysis.

```bash
make lint
```

Runs the configured `golangci-lint` checks across the Go code.

```bash
make lint-go
```

Runs `flutter analyze` for the Flutter app.

```bash
make lint-flutter
```

## Service Scripts

### Commands

Starts a session against the running service.

```bash
go run ./services/main-service/scripts/start-session
```

Sends one interaction request against the running service.

```bash
go run ./services/main-service/scripts/interaction --session "$SESSION_ID" --message "Hello"
```

Fetches the stored request analysis for one completed request, including structured signals and an optional
request-level intent summary.

```bash
go run ./services/main-service/scripts/analysis-request --request "$REQUEST_ID"
```

Fetches the stored analyses for all completed requests in one session, plus the aggregated session view and an optional
session-level intent summary.

```bash
go run ./services/main-service/scripts/analysis-session --session "$SESSION_ID"
```
